# Bug fixes relative to TU Delft SWAN 41.51

## Basis of comparison

This list compares the RWS fork with TU Delft's `upstream/main`:

- repository: [`citg/wavemodels/swan`](https://gitlab.tudelft.nl/citg/wavemodels/swan);
- upstream commit: [`43e9bbba393f2cf9eaff78bc92eaed118a3a5c8e`](https://gitlab.tudelft.nl/citg/wavemodels/swan/-/commit/43e9bbba393f2cf9eaff78bc92eaed118a3a5c8e), 13 July 2026;
- last source patch in it: `0dabfa4` (`updated src (patch B)`), also
  13 July 2026;
- version number on both sides: **41.51** (in this fork the parameter
  `SWAN_VERSION_NUMBER` in [src/swanmain.f90](../src/swanmain.f90)).

The merge base of the two lines is `43e9bbb`. The items below are therefore
local fixes on top of the same 41.51 source base, not differences between two
SWAN releases. File names refer to the modernised free-form source in this
fork; the TU Delft source is still entirely based on the `.ftn` form
(18 `.ftn` + 57 `.ftn90` under `src/`, not a single `.f90`) and is
preprocessed by `switch.pl` before compiling.

Which decks actually compute differently from that source base is not only
described here in prose, but also recorded in machine-readable form in
[upstream-delta.json](upstream-delta.json): per deck `identical`, `differs` with
the BF number, `fork only`, or `skipped` with a reason.
[scripts/upstream_delta.py](../scripts/upstream_delta.py) runs the decks
through the pinned upstream binary and through the fork and checks that claim;
[tests/test_upstream_delta.py](../tests/test_upstream_delta.py) guards the
inventory at every commit and runs the measured half under
`SWAN_UPSTREAM_DELTA=1`. A deck that starts to differ without a BF reference
therefore turns a gate red, instead of being discovered afterwards.

The qualifications mean:

- **proven**: the defect was reproduced before the fix and was gone after the
  fix, or was shown with a memory tool;
- **proven with a tool, consequence latent**: a memory or runtime check
  points to the defect, but on the decks tried the result did not change;
- **proven from the source**: the bug follows directly from the upstream data
  flow or a compiler diagnostic and the fix has targeted coverage, but there
  is no separate before/after measurement of a consequence a user would see;
- **latent**: the TU Delft code breaks a language, interface or internal
  contract, but the normal path that is covered did not dereference the wrong
  value;
- **diagnostics/build**: the computation has not changed, but a missing
  warning, error handling or build route has been fixed.

Combined qualifications occur where the defect itself is established but no
consequence appeared on the decks tried. The evidence column therefore always
separates what was **measured** from what was **derived** from the source;
where there is no before/after measurement of the numerical consequence, none
is claimed.

Two fixes (BF-01 and BF-05) only bite when one process runs more than one
computation. The standalone 41.51 binary runs one case per process; the way
to get there is an external coupler — the upstream source refers, in the
comment at `SWMAIN`, to `couple2swan.F`, which is not included — or the
library API of this fork. That does not make them any less real, but it does
decide who is affected.

## Bug fixes delivered

The items are grouped by what a user notices. The numbers were assigned in
the order the bugs were found, so they are not in sequence.

| BF-34 | **proven** | **`BREAKING ASYM` destroyed the wave field over the whole domain.** The asymmetry breaking index of Saprykina et al. The index is therefore bounded below by 0.6 and never becomes small, let alone zero. `BRKPAR` passes `BRCOEF = -1` for the second regime, after which `SINTGRL` computes `BRCOEF = PSURF(4) - 0.3*PSURF(5)*BIPH` — but only behind `IF (BIPH.LT.0.)`. That end point is not rare; three routes lead to it. With Eldeberky, `0.5*PI*(TANH(URCRIT/UR)-1)` underflows in single precision to exactly zero once the Ursell number is at or below 0.0699 (default `URCRIT` = `PTRIAD(4)` = 0.63): `TANH` saturates as soon as `1 - TANH(x)` drops below half an ulp of 1.0, so from `x` > 13·ln2 = 9.0109, and 0.63/9.0109 = 0.0699152. Measured with gfortran in single precision, step 1e−4: exactly zero up to and including `UR` = 0.0699, −9.362676e−08 at `UR` = 0.0700; a finer scan puts the threshold between 0.0699152 and 0.0699153, exactly where the derivation predicts it. The check has to be done in Fortran: numpy's float32 `TANH` saturates later and would suggest a threshold that is too low. Every point seaward of the surf zone therefore lands on that end point, and `UR` = 0 gives `TANH(Inf)` = 1 and so zero straight away. With Saprykina, `0.5*PI*(MIN(1,DELL/PTRIAD(9))-1)` is exactly zero over the whole regime `DELL >= PTRIAD(9)` — not an edge case but an entire region. ## Not counted as bug fixes

This list is only about bugs in the TU Delft version. Deliberately left out
are:

- the conversion to free-form Fortran, modules and explicit state ownership;
- the replacement of FFTPACK by FFTW3, the spatial index and other
  performance improvements;
- the extension of CMake, CI, tests, examples and verification tools, as far
  as no upstream bug was fixed in the process;
- removed dead code and compiler warnings without a demonstrated bug in
  behaviour;
- **the ESMF branch of `SWIND3`, `SWIND4` and `SWIND5`.** That branch refers to
  `KCGRD(1)`, and that looks like a reference to an argument that has been
  gone from these routines since SWAN 40.00. It is not: `KCGRD` is a module
  variable of `SWCOMM3` (`swmod1.ftn:2078`, `THREADPRIVATE`), all three
  routines do `USE SWCOMM3`, and the value is the current grid point. The
  branch was therefore valid in the TU Delft source and pointed to the right
  point. This fork replaced `KCGRD(1)` in these routines with an explicit
  `IGP` argument, so the dormant branch had to move along in the fork's own
  tree; in doing so it was made buildable as an ordinary CMake capability and
  covered by a backend test (`src/coupling/`,
  `tests/test_esmf_coupling_backend.f90`). That is modernisation maintenance,
  not a fix of upstream;
- the changed default physics since SWAN 41.45. That is a deliberate
  upstream change. `GEN3 KOMEN DRAG FIT` is a compatibility setting to
  approximate the 41.31 physics, not a bug fix in 41.51.

## Known open issues

These issues are in upstream and have been investigated, but not resolved:

- **A stop message does not prove convergence.** SWAN stops a stationary
  run when Hs and Tm hardly change any more between two iterations.
  Under-relaxation (`ALFA`) makes that change small, even when the solution
  has not been reached yet, and the criterion cannot tell those two apart. On
  `quad_dia1` the run stops at `ALFA=0.10` after two iterations and at
  `ALFA=0.05` after ten with "accuracy OK in 100.00 %" at Hs 1.278 m at
  25 km, and at `ALFA=0.01` after 40 iterations at 1.403 m. Computed on until
  the balance residual is at machine precision (about 1500 iterations), the
  same run arrives at 1.923 m. This is not a property of the fork: on
  `quad_dia2` upstream 41.51 and RWS 41.31A.1 behave the same way. At
  `ALFA=0.01` all three report 100%, while Hs at 25 km is a quarter below the
  run without under-relaxation (`doc/early-stop-by-version.json`). The
  mechanism has therefore been in SWAN since at least 41.31. Because a
  stationary growth problem builds up energy towards the balance, stopping
  too early ends too low; for design conditions that is the unsafe direction.
  The fork has an optional balance residual that does make the distinction
  (`NUMERIC ... RESIDUAL`, off by default; see
  [balance-residual-design.md](balance-residual-design.md)).
- **MPI does not fully fill in land outside the active area.** After BF-40,
  the wet field of the MPI assembly is equal to serial, but on land outside
  the active area not entirely: quantities that SWAN also fills in at
  inactive points (measured: `WIND`) are at the exception value in MPI in the
  rows below the first active point. Those rows lie outside every subdomain,
  because `SWBLADM` cuts a subdomain off at the envelope of its active points
  plus boundary strip. Fixing this requires a different domain decomposition,
  not a different collection step; no wet cell is involved.
- **How complete this list is.** Some defects were found by reading code that
  looks wrong and checking the pattern against `43e9bbb`, the others through
  compiler warnings, runtime checks, Valgrind, the comparison with upstream
  per deck and a systematic trial with wrong input. All 42 example decks have
  been run against upstream with the same compiler and `-O3`, and each
  difference was assigned to BF-15, BF-16 or BF-34, each time proven by
  reverting the fix and measuring byte-identity. That covers the paths these
  decks touch, not the branches outside them, and that is exactly where BF-15
  and BF-34 were. So there are almost certainly still bugs in upstream that
  are not listed here.

## Appendix: BF-34 against the literature

Kuznetsov, Saprykina & Volkova (2018), *Dependencies of breaking type, breaking criteria and energy dissipation on amplitude-phase frequency structure of waves*, Coastal Engineering Proceedings (ICCE 2018), paper 8566, gives the two regimes explicitly: for `E2/E1 > 0.35` gamma does not rise and is roughly uniformly distributed around the mean **0.6** — exactly the constant that `BRKPAR` assigns in that branch — and for `E2/E1 < 0.35`, `gamma = Hs/hb = 0.6 + 3.5*(E2/E1)^2` holds. The paper also gives the observed range of gamma: **0.4 to 1.2**. A breaking index of zero therefore does not occur anywhere in it, which confirms the fix externally as well, apart from the internal inconsistency. SWAN replaces the second branch with a linear function of the biphase, `gamma = PSURF(4) - 0.3*PSURF(5)*BIPH`. Both are anchored at 0.6 and run to comparable upper limits (paper 1.029 at `E2/E1` = 0.35; SWAN 0.977 at biphase = -pi/2). As a check, the formula from the paper was temporarily put into `BRKPAR` in place of the biphase branch — `E1` and `E2` are already available there — and run on `src_break_asym`: Hsig comes out at 0.5018 / 1.9361 / 2.3864 / 0.8246 / 0.5870 / 0.6188 m against 0.5018 / 1.9357 / 2.3860 / 0.8368 / 0.5841 / 0.5786 m for the biphase form, so equal to rounding level outside the surf zone, within 1.5% in the surf zone (1.48%) and 6.5% (6.50%) at the last point — each time with the paper's value as denominator, because that is the relation being reproduced; with the biphase form as denominator, that last point becomes 6.9%. The biphase branch therefore reproduces the relation from the paper within a few per cent. Note: the two regimes as the paper writes them down do not join up (1.03 against 0.6 at `E2/E1` = 0.35); they describe two clouds of points in a figure, not a single curve. This is therefore a consistency check against the published relation, not a validation against the measured series themselves.
